The problem

Why reading every line no longer works, even when the system does.

You described what you wanted, and the agent built it, filling every gap in your description with its own judgment. It works: people use it, it may even take payments. But you have no idea how the code does what it does, and you cannot find out by reading it. An agent can write ten thousand lines in an afternoon and the next feature the next day. No person can read that much, and the usual code review, where someone reads the lines that changed and says whether they look right, stops being possible. Testing does not close the gap either: you can only test what you know to look for.

Reading the lines would not find the problems anyway. Code an agent writes is clean on its surface: it compiles, it is tidy, it looks right. The mistakes that matter are mismatches between what the code does and what the system was meant to do: a step skipped, a rule applied in the wrong place, a part that depends on something it should not, a failure nobody handles. Those are questions about the design, and code is a poor place to answer them.

Picture a house built by a crew that filled every gap in the drawings with its own judgment. The drawings did not say how to get from the garage to the bedrooms at night, so the crew cut a door straight from the garage into the children's bedroom. It is well made, it closes nicely, and no architect would allow it. Neither would you. Nobody should move in until someone has walked every room and seen what was actually built. Software built by an agent is that house.

The idea

A home inspection for software systems.

The way to find that door is not to read the drawings again; it is not on them. It is a home inspection: walk every room, open the panels, see what was actually built, and write down what is sound and what needs attention. BigBrain System Visualizer is that inspection for software. It lets you view every square foot of the system, review it room by room, ask your own coding agent to explain any part of it, and approve everything you are creating. You walk what was built, instead of reading how it was written.

BigBrain System Visualizer, BigBrain Visualizer for short, shows the whole system as a 3D map, and the system is more than its code. The map holds the parts of the code and the connections between them, the cloud resources the code runs on, since much of what can go wrong is in the gateway, the storage or the network rule rather than in any line, and the tests built for it, so each step shows which tests check it. The scenarios run through all of it, laid out so that someone who does not read code can walk the map and follow what the system does. Your agent reads the code and draws the map; you play the scenarios that matter, ask questions, leave comments and To Do's, and mark each part inspected. A developer or a specialist walks the same rooms with the detail they need: files, functions and the cited lines a click away. One map, with the plain words on top and the technical ones underneath, so the owner, the developer and the specialist can talk about the same thing, and the owner can say, having seen it, that the system does what they asked for and nothing else.

A home inspector knows where to look and what to ask. Most owners do not, and the app does not expect you to. It comes with a stock question for each area that matters in any system: security, reliability, performance and scale, maintainability, data, cost and testing. Each is put to your agent with one click and counted in the inspection. When you are looking at a part or a step and do not know what to ask, What should I ask? proposes the questions worth asking about exactly that. And What if plays what happens when a step goes wrong: the payment fails halfway, or the same payment event arrives twice. Promises are the rules you could say in your sleep, in your own words: a person is never charged twice, nobody can see another member's bookings. Your agent checks each one against the code and answers guaranteed, not guaranteed and what could break it, or could not settle it, and says whether a test checks the rule itself. Together they turn a walk through the system into an inspection that brings out the issues that need addressing, including the ones you did not know to look for.

Even with that help, a review by a human expert you trust still matters. The usual price is high: source access to grant, a repository to open, and agreements to sign before anyone looks at anything. BigBrain Visualizer lets you share some or all of your system instead: the scenarios you choose, with the parts of the map and the cloud resources they pass through, in one file that carries no source code. The reviewer opens it in a free viewer, walks it apart from your code and your Mac, and leaves findings, comments, To Do's and questions. You bring the file back in, go through each recommendation with your own agent, which has the code to answer with, accept what belongs in the map, and turn it into work to do.

How it works

From a folder to a map you can walk, in five steps.

1

Pick a folder

Choose one checkout. Your agent finds what it works with outside that folder and suggests the others on your Mac, with its reason. You decide which to include.

2

The agent draws the map

It reads the code, lays out the parts and connections, walks through each scenario it finds, and catalogs every feature. With Cloud on, it reads the cloud resources the system runs on and sets them above the parts that use them. Find the Tests records the test suites and cases, so each step shows which tests check it. The map builds in stages, so you can start walking early.

3

Walk and play

Go inside a part and back out. Play a scenario step by step, read aloud, with what is sent, what comes back and what can go wrong. Summary in plain words; Detailed adds the files and code.

4

Ask and note

Ask the agent about the step on screen and get an answer with its citations. Leave comments, To Do's and questions on the parts and steps they belong to.

5

Inspect, report, fix

Run an inspection with your team or a specialist, close it with a report, and send the To Do's to your agent to fix. You approve each change in your own project.

What this looks like

Four reviews, none of them by reading code.

The owner

An owner who does not read code reviews what the agent built

The owner built the booking app with Claude Code and has never read its code. Members book and pay through it, and it has worked for months. On the map they see the pieces they know, the app, the backend, the payments, the data, and one they do not: a part that runs every night. They ask the agent what it is. It is a job that emails members who have not booked in a month, added while the agent built sign-up reminders, and nobody asked for it. Their door from the garage, found without reading a line. They leave a Must do To Do to remove it, then play the booking scenario, hear each step, and ask what happens if the payment fails halfway.

The team

A team inspects a release while the project manager watches it come together

Before the release goes out, the team lead starts an inspection and shares the library through a private git repository. The engineers join from their own Macs and each takes the parts they know best: one walks payments, one the data, one the jobs that run at night. They play the scenarios, ask the agent questions, leave comments and To Do's marked Must do, Should do or Nice to have, and mark each part inspected when it is done. The project manager, who reads no code, follows the same map. The Coverage view colors it by who has looked at what and shows the parts nobody has reached yet, and the Readiness card says which stages are done and what is still waiting. When the last part is marked, closing the inspection writes the report: who took part, what was covered and what was not, how the code moved during the inspection, and the To Do's grouped by priority.

The outside expert

An expert reviews the system without ever seeing the code

Before launch, the owner wants a security reviewer they trust to look at how payments and personal data move through the system. The reviewer is not on the team and must not be given the code or the repository. The owner selects the scenarios that matter and sends one file: the map and those scenarios, with no source code in it. The reviewer opens it in the free viewer, plays each scenario step by step, goes inside the parts it passes through, and leaves findings, comments and To Do's, with a question for the owner's agent where the map is not enough. They send the file back. Nothing enters the owner's map until the owner accepts it; then the review is part of the map, and the code never left the owner's Mac. An architect or an auditor is brought in the same way.

The next release

A second release inspects only what changed

The next release is the smaller job, because BigBrain tracks what changed and lets the inspection focus on it. Each inspection keeps a snapshot of the map it inspected. When the next release is ready, the team starts a new inspection and chooses to inspect what changed since the last one. New parts are green, parts whose job or connections changed are amber, and everything that did not change fades away. Each person takes the changes they know best, the sidebar lists the changes nobody has reached, and the report says, change by change, who looked at it.

What makes it different

The code is still there when you want it. It is the last step, not the first.

  • Compared with a diff. A diff shows lines. The map shows the system, the scenarios a change touches, what else is affected, and what to test again.
  • Compared with an architecture diagram. A diagram is drawn once and goes stale. The map is built from the code, updated from the commits, and every part cites the files it stands for. It can be walked, questioned and annotated.
  • Compared with chatting with an AI about code. A chat has no shared picture, and the answer scrolls away. Here the question carries what you are looking at, the answer is kept on the part it is about with its citations, and people in an inspection see the same map and each other's notes.

In each case the people stay in charge of the design. The agent explains and proposes; people decide what is good, what must change and how urgently, and approve every fix in their own tools. AI can write more code than people can read. BigBrain does not ask people to read it. That is what a review was always for.

Privacy

Your code never leaves your Mac.

Nothing about your system is sent to us. The one server the app talks to knows who has a seat, and nothing else.

Code stays in your checkouts

Your agent reads the code on your Mac, under your own account with its provider. The cloud is read the same way, through your own sign-in and read only. Everything BigBrain learns is kept in a library folder on your Mac, never in the project and never with us.

The service holds an email and a seat

Our license service holds the email your sign-in provider verified, a device hash for each Mac, your seat and license state, and a log of sign-ins and activations. No map, note, question, code or folder path can reach it.

No password, no key

You sign in with Apple, Google or Microsoft and we never see a password. BigBrain has no AI of its own and asks for no API key; it runs the agent you are already signed in to.

Signed and notarized

Each build is signed with an Apple Developer ID and notarized by Apple, and the app updates itself from then on. The Security Policy says how to check a build by hand.

Everything cites the code

Each fact, step and answer points at the files and lines it came from, and BigBrain checks that every citation resolves before it keeps it. Text the code does not back is not kept.

A sent file carries no source

The file a specialist receives holds the scenario and the part of the map it walks through, and no source code. The demos, the viewers and sent files need no account at all.

The details are in the Privacy Policy and the Security Policy.
