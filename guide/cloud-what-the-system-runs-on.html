Cloud: what the system runs on

Much of what a system does, and much of what can go wrong with it, is in the cloud it runs on rather than in its code: the gateway in front of an API, the storage account, who may call a function. The Cloud tab reads it from Azure, AWS and Google Cloud and joins it to the map. The demo shows a system on both Azure and AWS, from made-up accounts that are never read.

BigBrain only reads, with your own sign-in. It keeps no password, key or token, and never changes anything in your cloud. Before every command that reaches the cloud, it shows you the command, what it reads and why, and runs it only when you press Run. Commands that are not reads are refused in the code, whatever asks for them. Setting values, keys and connection strings are dropped before anything is written; only names are kept.

Getting started

The Cloud tab takes you through three steps.

  1. Sign in to each cloud the system uses. Sign In… opens Terminal on Azure's own az login; sign in there with an account that can read the subscriptions, then come back to BigBrain. BigBrain shows what it will read to finish (a short-lived access for each subscription) and, when you press Run, keeps that access in memory and deletes the sign-in files at once. Nothing of your sign-in is kept on disk. The access lasts about an hour; then the tab says your sign-in has ended, and you sign in again (what was already read stays). Quitting BigBrain ends it. Each sign-in adds to the ones you have, so a system that uses two Azure accounts can read both. Check Role… says whether a sign-in can only read; Sign Out forgets the access at once. Your own az in Terminal is never used or changed.

    Each cloud's row needs that cloud's own command-line tool on your Mac: az for Azure, aws (version 2) for AWS, gcloud for Google Cloud. When one is missing, its row says so in one line. On a system that does not use that cloud, the line is a quiet "Not set up on this Mac." On a system that does (an account or a reading of it, or code that names it), it is orange: "This system uses AWS. Install its tool to read it." Either way, Set Up… under the line says what the tool is, gives the command that installs it (brew install azure-cli, brew install awscli or brew install --cask google-cloud-sdk) with a Copy button, and has Choose Where It Is… for a tool installed somewhere BigBrain does not look.

    AWS has its own row. Sign In… offers two ways: With Single Sign-On opens Terminal on aws configure sso, where you sign in in the browser and choose the account and a role that can read it (such as ReadOnlyAccess); With an Access Key opens it on aws configure, where you type the key of a user that can only read. When the profile is written, BigBrain shows what it will run to finish: short-lived keys for the account (about an hour; an access key is turned into keys that last an hour, so BigBrain never keeps it), who you are, the account's name, and the end of the single sign-on session made for BigBrain. On Run, it keeps the keys in memory and deletes the sign-in files at once. The sign-in happens in a folder of its own, so your own ~/.aws files and sign-ins are never read, used or logged out. Each sign-in is one account; Sign In to Another… adds more. Check Role… looks up the policies of the role you signed in as.

    Google Cloud has its own row, and works the same way: Sign In… opens Terminal on Google's own gcloud auth login. Sign in with an account that can read the projects the system uses, then come back; BigBrain shows what it will read to finish (a short-lived access for your account), keeps it in memory when you press Run and deletes the sign-in files at once. One sign-in reads every project your account can see. Your own gcloud in Terminal is never used or changed.

  2. Choose Resources… opens one sheet. Tick the subscriptions the system uses, then BigBrain lists every resource in them, grouped by resource group, and ticks the ones the code and the map point to, with the reason ("The code names lotuslane-booking-func.azurewebsites.net", "The map's outside part Azure AI Foundry is …"). Tick or untick until the list is this system's, then Save, and Read Details reads the apps and gateways you chose: functions and who may call them, access rules, APIs and their policies. Each list is shown, with what it reads and why, before it runs. Each account then has its own row with Refresh, which reads its chosen resources again and tells you about new ones in their resource groups.

    For AWS, the sheet starts with the accounts you are signed in to and the regions to read (your sign-in's own, and those the code names; change them as you need). BigBrain first asks whether Resource Explorer is on in the account: where it is, one search lists every resource in a region; where it is not, BigBrain asks each service for its list, which is a longer list of commands to approve but finds the same. An owner of the account can turn Resource Explorer on in the AWS console. The resources are grouped by region, with IAM, S3 and CloudFront, which are in no one region, last. Read Details reads the Lambda functions (who may call each, and the handler it runs), the API Gateway APIs (which methods check the caller or need an API key, where they send calls, rate limits) and the S3 buckets (whether public access is blocked). Bedrock shows as one part per region, with only the models your code names. Refresh tells you about new resources in the chosen ones' regions.

    For Google Cloud, Choose Google Cloud Resources… does the same with your projects: it lists them, then every resource in the ones you tick, grouped by kind, through Google's Cloud Asset Inventory. That needs the Cloud Asset API turned on in each project. Turning it on is a change to your project, so BigBrain never does it; if it is off, BigBrain tells you the command to run yourself (gcloud services enable cloudasset.googleapis.com --project=<your project>, or turn it on in the Google Cloud console under APIs & Services), and lists the other projects meanwhile. Read Details reads who may call each function and Cloud Run service, where an API Gateway sends calls and what it checks, and whether a bucket is public. Refresh on a project tells you about new resources in it.

  3. Cloud mapping. BigBrain connects the chosen resources to the parts that use them on its own. Review Cloud Mapping… shows each part with its resources and the reason for each link; add what it missed and take out what is wrong.

The Cloud tab

What was read, by kind: gateways, front doors, hosting, data, messaging, workflows, messages to people, identity, secrets, network, AI and other services, and watching. Click a cloud part to see its addresses, how it checks who is calling, its functions or APIs, and what it is linked to. Questions for the inspection, in orange, are what the rules found worth asking: a gateway whose app can be called directly, around the gateway's key check and rate limit; web functions anyone may call (on AWS, a Lambda function URL that needs no sign-in, or a policy that lets any AWS account call it); containers or buckets anyone may read; cross-site calls allowed from any website. On Google Cloud, also: a function or Cloud Run service anyone on the internet may call, a bucket anyone can read, and an API Gateway API that asks for no API key and checks no sign-in.

Cloud Mapping

Review Cloud Mapping… lists each part of the system with the cloud resources it runs on or uses, like the project folders in Settings > Library. BigBrain fills in what it can tell: the code names an address the cloud part answers, the code declares a function the Function App runs, a gateway sends calls to the app's address. On AWS also: the code names a table, bucket, queue or topic by name or id, exports the handler a Lambda function runs, or calls a Bedrock model, and API Gateway sends calls to a Lambda function. Each link says why. Link adds one it missed; the cross takes out one that is wrong. Your choices are kept in the library and win over what BigBrain finds.

On the map

The Cloud checkbox above the map (View > Show Cloud), like Tests, draws the cloud parts on a level above the map, colored by kind, each linked to the parts that use it, and gateways linked to the apps behind them. An orange ring marks a cloud part with a question; an orange path runs from the parts that call a gateway straight to the app behind it when that app can be called directly. Point at a cloud part to see what it is; click it to fly to it and show its details under the Cloud tab's list; double-click it to open its details over the map. When the map already has an outside part for a cloud resource (an "Azure Blob Storage" the agent named from the code), the resource is drawn on that part instead of twice; Cloud Mapping shows the match as "Is", and you can take it out or add one. Cloud first, in the legend, quiets the parts with no cloud link, so the map shows how the system meets its cloud. Off, the map is as simple as before.

Scenarios through the cloud

With the Cloud checkbox on, a scenario walks through the cloud parts its calls pass through. Between the app calling and the function answering come steps such as "Through lotuslane-apim" (what the gateway checks: keys, rate limits, rewrites, and any question about it) and "On lotuslane-booking-func", drawn as discs above the path and read aloud like any step. They come from what BigBrain read from the cloud, not from the saved scenario: turn Cloud off and they are skipped. A movie recorded with Cloud on shows and reads them too; with Cloud off it is the scenario as saved. Comments, To Do's and tests stay on the scenario's own steps; a note made on a cloud step goes on the step the call is on its way to.

Cloud questions

When a cloud part is selected, or a scenario is on a cloud step, the agent pane's stock questions become Cloud questions: Who can reach it, Ways around, Keys and identity, If it fails, Cloud cost, and Matches the code? Each is one agent run, like the stock questions (about $1 to $2). The agent is given what BigBrain kept about the cloud part (its name and type, security notes, functions, policies in words, links and questions) with no host names, addresses or ids, and never a secret; it reads the code for the rest and never reaches the cloud itself.

To ask, click Ask on a question in the Cloud tab's "Questions for the inspection", or on a cloud part's details (under the Cloud tab's list, or over the map). The agent pane opens with that cloud part as what you are asking about, and with the question already in the field, ending "What in the code explains this, is it a risk, and what should change if it is?". Change it or press Ask to send it; or click a Cloud question, or type your own. A cloud part with no question leaves the field empty. Selecting the cloud part and opening the agent pane yourself (⌥⌘A) does the same. Ask shows when no scenario is open; in a scenario the agent pane asks about the step you are on.

From the command line: bigbrain cloud check, accounts, find, add, read, list and join (see bigbrain --help), each asking before it runs a cloud command. They use your own az, aws or gcloud sign-in in Terminal. For AWS, add --provider aws to check, accounts, find and add (with --account <account id> and --region <region>), and set AWS_PROFILE to the profile for the account before read. For Google Cloud, add --provider gcp to check, accounts, find and add (with --account <project id>). read reads every account chosen for the system.
