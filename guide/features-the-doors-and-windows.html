Features: the doors and windows

The Features tab lists everything the system does. It is filled in two ways.

What BigBrain finds in the code by itself. With fixed rules and no agent run, BigBrain lists what starts things: every server address the code answers, every job set to run on a schedule, work started in the background, messages it listens for (queues, events, links opened in the app), and every channel between parts of a desktop app. And what the system changes or reaches: calls to other services, emails, texts and notifications, payments, other programs started and links opened, files written or deleted, stored records written or deleted, and the tables it keeps data in. Your own patterns from Settings > Features are added. It costs nothing and each entry points to an exact file and line; a kind of action in one file is one entry, with how many more lines do the same. But it is raw: no words about what each is for, and nothing the rules do not recognize, such as a button in the app or work done at startup. The rules look for the calls that do these things, so they find them whatever an agent says about the code; they find too much rather than too little. Before there is a catalog, the tab shows this list, in groups. An entry no scenario shows is in orange, with Add Scenario… (start a scenario there) and Suggest Scenarios… (the agent suggests some through its part); Only those no scenario shows narrows the list.

The catalog your agent writes. Catalog Every Feature… (one agent run; New System runs it after the build when Features is ticked) has your agent read the code and write the list a person would recognize. It groups the raw entries into features (on one system, 130 server addresses became 65 features), and for each says in plain words what it does, what starts it, what it changes (records written, updated or deleted, settings, permissions, money inside the system), what it reaches (emails and texts to people, payments, data sent to other companies), and which scenarios show it. It can also find what the rules cannot. It is the agent's judgment, so it can be wrong; BigBrain checks every citation. Both Catalog Every Feature… and Catalog Again… open Update with Features ticked, which says first how many features there are, how many rest on code that moved, what the rules found that no feature names, and that it is a full agent run paid for from your plan, the longest kind after building the map. Settings > AI Agent sets a spending limit per run.

Two checks that the agent was asked about everything

The catalog is the agent's disclosure, like a builder's list of what they built. BigBrain makes sure the agent was shown everything and had to answer for it, with two checks that need no agent:

  • Everything found in the code is in a feature. The agent is given every entry the rules found and must place each in a feature that says what it does. Each feature shows the entries it covers on its In the code line (hover it for the files and lines). Any entry the agent left out is listed in its own group, In the code, not in any feature, in orange. Each row says in plain words what the code does (starts work that runs on its own, waits for something from outside, calls another service, sends emails), where it is, and the code's own words in small print, with a sentence on why that kind of code matters. Ask What This Does has your agent read it and say what it does, what starts it, and which feature should name it, or whether it is plumbing a feature relies on; Add Scenario… shows it on the map.
  • Every source file is accounted for. Every file of code written by hand (not tests, not generated, not settings files) must either do the work of a feature (a feature cites it or names it, or it holds an entry a feature covers) or be explained by the agent: shared code features use, building and installing, settings, test support, not used, or other, with a sentence. Files with neither are listed under Code files no feature accounts for, in orange. The files the agent explained are under Other code, as your agent explained it, so you can read each explanation and judge it: ✓ Agree, or ✗ Disagree with why (and, if there is something to do, a Must do To Do for your coding agent, such as removing a file nothing uses). A file you disagree about counts as not accounted for and moves to the orange group with your reason; the next Catalog Again is told you disagreed and why, must put it in a feature or explain it differently (the same words are refused), and its new explanation comes back for you to judge. An explanation never excuses an entry the rules found in that file: that entry must still be in a feature.

These checks make the agent account for everything; they do not make its reading careful everywhere. The agent cataloging is usually not the one that built the system and has no reason to hide anything, but it can miss things honestly: it believes the builder's function names and comments, it reads something odd as part of a nearby feature, it sums up several behaviors in one sentence, and in a large file it reads some parts quickly. A file that does most of its work for a feature you know can hold a few lines that do something else. Read the features, and the In the code line of each, with that in mind; asking about a feature or a file (right-click it) is the way to look further. A much deeper review, function by function, done now and then rather than every time, is planned as a second phase (see Inspecting a system).

Once there is a catalog, the tab shows the catalog only.

Using the catalog

Each feature has two buttons on its left:

  • ✓ Approved: you asked for it, or you want it. Its name turns from orange to black.
  • ✗ Not approved: nobody asked for it, or it should work differently. BigBrain asks why (optional) and what to do:
    • Remove it or Change it (say how) writes a Must do To Do on the feature's part. The To Do carries what the feature does, what starts it, what it changes or reaches, and the code it rests on, so Review To Do's and Fix Now hand all of it to your coding agent.
    • Decide later marks it not approved with no To Do yet; Make To Do… on the feature writes one when you know.

    A feature not approved is shown in red, in a group of its own, Not approved, with your reason and Show To Do. Once the fix is in, Update with The map and Features ticked; the feature disappears when the code no longer does it.

Click a button again to take the decision back; a To Do already written stays in the notes. Your decisions are kept when the catalog is written again.

The other features are in two groups, Happens by itself and Done by people, closed to start with so you see each group and its count; click a group to open or close it. Three buttons at the top narrow the list:

  • To decide: features with no decision yet, in orange. Approve or not approve each one.
  • Not walked through: features no scenario shows. For each one that matters, Add Scenario… starts a scenario there, and the agent walks it through from the code.
  • All: every feature.

The ones to look at first are both: not decided and not walked through. The count beside the tab's name is how many of those there are, plus any entries in the code no feature covers.

A scenario shows a feature when the catalog names it. A scenario that only passes through the same part is listed in gray, "Through the same parts, not shown to use it", and does not count: a part may hold many features, and a scenario through it may never touch this one.

  • Click a feature to see it on the map. The map opens the level that holds every part the feature passes through, lights those parts in gold, numbered in the order the feature passes through them, with the connections between them, and darkens the rest. The panel below the sidebar shows the feature itself: what it does, what starts it, what it changes and reaches, its parts in order (click one to go to it), what in the code it covers with file and line, the files that do its work, and the scenarios that show it, with Approved and Not approved. Done, Escape, or clicking the feature again puts the map back.
  • Click a scenario under a feature to walk it. Right-click a feature to show it on the map, add a scenario, show its first part, or ask about it.
  • A feature whose code changed since it was cataloged says so; Catalog Again corrects it and adds what new code brings, keeping your decisions. A feature the catalog returns as it was is confirmed: it is stamped with the commits the run read, so it stops counting as resting on code that moved.
  • If your plan's usage limit is reached part way, the catalog waits for it to reset and carries on in a new session, keeping what it had written; if the reset is more than eight hours off, it stops, and Catalog Again carries on later. Find the Tests and the technical descriptions carry on the same way.

Settings > Features (advanced) says what else counts as a feature in the open system. Patterns are looked for in the code with no agent run and listed in the tab under their own names: for example "Emails sent", looking for send_email(, or "Card charges", looking for paymentIntents.create, as plain text or a regular expression, optionally only in some files. For the agent, in your words is read when the agent catalogs the features or suggests scenarios: "Treat every place a member is charged or refunded as a feature." Both are kept in the library beside the map (feature-definitions.json), so a shared library shares them.

Test and tool folders. Folders named tests, test, __tests__, spec or testdata, and files named like FooTests.swift, test_foo.py or foo.test.ts, are read as tests by themselves: for what they reference, never for what they do, so a timer or a table a test plants in a pretend project is not a feature. Any other folder of a project that is not the product is for you to say, and it is one of two kinds. Tests and fakes (a test harness, fixtures, mocks, a sample project) are read the same way as tests: nothing they do becomes a feature. Tools (build, release and developer scripts) are read in full, because a reviewer may want to see what a release script reaches, but what they do is listed apart from the product's features, under Tools at the end of the Features tab; no feature explains them and no scenario is expected to show them. When a system is set up, the agent that reads the project to find what it works with also lists such folders, each with its kind and its reason. BigBrain only suggests; you decide, and can change any decision later. The window lists every such folder under its project, each saying why it is there: read as tests by its name, suggested by your agent or added by you. A suggested or added folder has its kind and Count as Product, which takes it off the list so it is read as part of the product. A folder read as tests by its name has Count as Product too, for a folder that only looks like tests (a testing tool's own Tests folder, an API's spec); Read as Tests undoes it. You can also add folders when a project is added, or later under Test and tool folders in Settings > Library, one list per project. They are kept beside the map (test-folders.json) and read from the next Update; until then the note above the sidebar says the catalog is due.
