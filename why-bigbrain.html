Why BigBrain System Visualizer

BigBrain System Visualizer, BigBrain Visualizer for short, is a Mac app that explains a software system as a 3D map you walk through, built from the code by the coding agent you already have. This page is the case for it: the problem, the idea, how it works, and what it looks like in use.

Back to the product page
The problem

Software that works, more or less, and that no human can honestly say they have reviewed.

An AI coding agent can write ten thousand lines of code to add a feature in an afternoon. The next feature follows the next day. No person can read that much code to find what is wrong with it, and the traditional code review, where a person reads the lines that changed and says whether they look right, stops being feasible.

Imagine a house built from an architect's drawings by a crew that worked fast, never asked a question, and filled every gap in the drawings with its own best judgment. The drawings did not say how the family would get from the garage to the bedrooms at night, so the crew cut a door straight from the garage into the children's bedroom. It saves a walk around the house in the rain. It is well made, square, and it closes nicely. The architect would reject it on the spot: a garage is kept apart from the rooms people sleep in because of exhaust fumes and fire, and no convenience is worth that. But the architect was not asked, and the door does not appear on any drawing. The family could live in that house for a year and only find out when something went wrong. Nobody should move in until someone has walked every room and seen what was actually built.

Software built by an agent is that house. Take someone who has never written code and has built a real application with Claude Code: customers use it, it takes payments, it works. They described what they wanted, the agent built it, filling every gap with its own judgment, and they have no idea how the code actually does it. How do they know nothing like that door was built in? A step the agent added because it seemed sensible, a rule nobody asked for, data kept that should not be, a shortcut taken under a corner nobody described. You can test such an application for a long time and never run into a feature or an implementation that was not intended, because you only test what you know to look for.

Reading the lines would not find the problems anyway. Code written by an agent is clean on its surface: it compiles, it is tidy, it follows the conventions, and it looks right. The mistakes that matter are not typos or slips a reader could catch. They are mismatches between what the code does and what the system was meant to do: a step that was skipped, a rule applied in the wrong place, a part that now depends on something it should not, a failure nobody handles. Those are questions about the system's design and its intentions, and looking at code is a poor way to answer them.

  • A diff shows lines, not the system. A diff, the list of lines added and removed, says what changed. It does not say what the system does, how its parts depend on each other, or what else the change puts at risk.
  • Owners are shut out. Many people who own AI-built software do not read code. The two explanations on offer, technical jargon or the code itself, leave them unable to say whether the system does what they asked, where it is fragile, or what to test after a fix.
  • The volume only grows. Whatever a team can review by reading today, the agents will outrun tomorrow.

The result is software that works, more or less, and that no human can honestly say they have reviewed. The review has to move up a level, from the code to the design the code is supposed to serve: a view of the whole system that a non-coder and a coder can both walk, question and judge.

The idea

A design review, not a code review.

Back to the house. The way to find that door is not to read the drawings again; it is not on them. It is a home inspection. An inspector does not read blueprints line by line. They walk the house room by room, see how it is lived in, open the panels to check the plumbing and wiring, and write a report: what is sound, what needs attention, and how urgently. The owner, who is not a builder, reads the report and decides what to fix.

BigBrain does the same for software. Your own coding agent reads the code and builds the map; you walk it, play the scenarios that matter, ask questions, and leave comments and To Do's, alone or in an inspection with other people. The review is of the scenarios and the design, with the algorithms and the code a step away when they matter. That is what a code review becomes when nobody can read all the code: a design review, which humans can take part in again.

It has two jobs, for two kinds of person. The first is to make sure a system an AI agent built does exactly what was asked for, and nothing else: no door cut from the garage into a bedroom. The second is to let someone who has never written code walk through a system and understand it, while a developer or a specialist walks the same map with the detail they need. One map, with the plain words on top and the technical ones a click away, so the owner, the developer and the specialist can talk about the same thing.

The second job is as much the point as the first. A newcomer should be able to open a map and, in a few minutes, know what the system is made of and what it does. The developer gets the same map in Detailed mode, with files, functions, data shapes and the cited lines open beside the words, and the specialist gets the lens for their trade: money, personal data, who may enter, what reaches outside. Understanding is not a technical privilege, and detail is not hidden from those who want it.

How it works

From a folder to a map, then room by room.

The examples here come from the app's demo: the booking app of a made-up yoga and pilates studio. Its owner knows the studio inside out and code not at all; a coding agent wrote the app, and the owner has never read it. Members find a class on their phone, book a place and pay by card. Behind the app, a booking backend and a set of emails and nightly jobs run as cloud functions, the data sits in a cloud database, and class suggestions come from an AI model. Everything described below can be opened and tried in the demo, and three narrated tours show it in the order it happens: setting up a new system, inspecting it, and inspecting its next release.

From a folder to a map

The owner chooses New System and picks one folder: the app members use. The coding agent reads it and finds what it works with outside that folder: the booking backend, the payment service, the phone's notifications. BigBrain suggests a folder for each one it can find on the Mac, with its reason ("it declares the routes the app calls"), and the owner decides: keep the backend's folder, add the project with the jobs, and leave the payment service and the notifications as outside parts. The agent then reads all three projects and draws the map, walks through each scenario it found, and catalogs every feature. If the owner wants, the clouds the system runs on are added too, now or after the review.

Then the inspection, room by room

  • Walk the house room by room. The system is a map of parts, from the big pieces an owner already knows about (the member app, the booking backend, the messages and nightly jobs, the studio's data, the payment service) down to the modules and functions inside them. You go inside a part to see what it holds, and back out to see where it sits.
  • See how it is lived in. A scenario walks through one thing the system does, step by step: Book a class, Cancel a booking, Reminder the day before. Each step says what is sent, what comes back and what can go wrong ("the save fails after the card was charged"), and the camera flies to the part where it happens. Play reads the steps aloud.
  • Find every door and window. The Features tab lists everything the system does, what starts it and what it changes or reaches, and the owner marks what they asked for. One stands out: a job that runs every night and has an AI model write to members who have not booked in a month. Nobody asked for it.
  • Check the plumbing and wiring. Each step and part shows the data it handles, the errors it can raise, and which tests check it. With Cloud on, the cloud resources sit above the parts that use them, and the questions for the inspection BigBrain finds there (an email function anyone on the internet can call) are listed to decide.
  • Note what is good and what needs fixing. A comment records something worth knowing. A To Do records work to do, with a priority: Must do, Should do or Nice to have. The owner's first is a Must do: make sure nobody pays for a class without a place.
  • With an expert at your side. The agent pane sends your question, together with what you are looking at, to your own coding agent. It reads the code and answers on the spot, with a one-line takeaway and the places in the code it relied on: "What happens if the payment fails halfway?" What should I ask? proposes the questions worth asking about the step on screen.
  • Bring in others. An inspection records who looked at what, so the map shows what nobody has reached yet. People on the team share the library; a specialist outside it, such as the payments consultant the owner trusts, gets one file with just the scenario, or just what changed, and sends it back with their notes.

Depth is on demand. Scenarios and design come first, in plain words. The Summary and Detailed switch adds the technical explanation, files and code references when you want them. You go inside a part when a question needs it, and you ask the agent about an algorithm when the scenario is not enough. Nobody has to read code to take part; anybody who wants to can get to it in two clicks. For the person who is new to the system, Jobs groups the parts into what they do together, in plain words; Screens lists the app the way its owner knows it; a glossary explains each technical word for this system; What if plays what happens when a step goes wrong; and the Readiness card says what to look at next.

Behind the map

  • Your agent builds it. BigBrain has no AI of its own. It runs the coding agent you already have, Claude Code or GitHub Copilot, with tools that let it read the code and hand back what it found. How long a map takes depends on how large and complex the system is. It is built in stages, so you can walk the map while its scenarios and features are added. A question costs about what one agent run costs.
  • Everything lives in a library, never in the project. The map, the scenarios, the answers, the notes and the inspections are files in a library folder of their own. BigBrain never writes into the project it maps, so it cannot change what that project ships.
  • The map stays current from committed code. When new commits land, BigBrain says so, and Bring the Map Up to Date reads what changed and shows the difference.
  • Fixes go to your own coding agent. Fix Now prepares a prompt for a To Do and opens it in your agent. You approve every change there, in your own project, as you always do.
  • Everything cites the code. Each fact, step and answer points at the files and lines it came from, and BigBrain checks that every citation resolves before it keeps it. Text that is not backed by the code is not kept.
Key scenarios

What it looks like in use.

The stories follow the studio from the demo: its owner, a teammate who runs the front desk, a payments consultant from outside the team, and a developer the studio hires.

An owner who does not read code reviews what the agent built

The owner built the studio's booking app with Claude Code. Members book classes and pay through it, and it has worked for months. The owner has never read its code and could not say what is in it. They open the map in Summary mode and see the pieces they know, the app, the backend, the payment service, the database, and one they do not: a part that runs every night. They ask the agent what it is. It is a job that emails members who have not booked in a month, something the agent added while building sign-up reminders and nobody asked for. It is their door from the garage: no amount of testing would have found it, because nobody knew to look. They leave a Must do To Do to remove it. Then they play Book a class, hear each step read aloud, what is sent, what comes back, what can go wrong, and ask "what happens if the payment fails halfway?" The answer is in plain words with the code it rests on. They have reviewed their application without reading a line of it.

You can walk this review yourself: the app ships with the studio's system as its demo. In the Features tab every feature is approved but one, the nightly emails to quiet members. Show it on the map, ask the agent what the part that runs every night is, mark it not approved and see the Must do To Do appear. Play Book a class, ask what happens if the payment fails halfway, and turn on Cloud to see the same booking pass through the system's two clouds. The demo needs no AI agent and no cloud account: its answers were saved with it, and its cloud is made up. Play the Tour walks through all of it with a voice and a pointer that clicks for you.

Three people inspect the first release

Before release 1.0 goes out, the owner starts an inspection called Release 1.0 walkthrough and shares the library through a private source repository. The teammate joins from their own Mac. Each walks the parts they know best, plays scenarios, asks questions and leaves To Do's. The Coverage view colors the map by who has looked at what, and shows the parts nobody has reached yet. When a part is done, whoever checked it clicks Mark Inspected. Close Inspection writes a report: who took part, what was covered and what was not, how the code moved during the inspection, and the To Do's grouped Must do, Should do, Nice to have.

A second release inspects only what changed

Each inspection keeps a snapshot of the map it inspected. When release 2.0 is ready, the owner starts Release 2.0 walkthrough and chooses to inspect what changed since the 1.0 walkthrough. BigBrain compares the two maps: the new waiting list and gift cards are green, the parts whose job or connections changed are amber. Coverage fades everything that did not change, so the owner and the teammate each take the changes they know best, and the sidebar lists the changes nobody has reached. The consultant, outside the team, is sent one file with just what changed; what they look at counts in the inspection when the owner brings the file back. The report says, change by change, who looked at it.

An inspector checks the testing

The owner wants to know whether taking the payment is tested. They ask BigBrain to Find the Tests; the agent reads the test code and records the test suites and cases. The Tests checkbox colors the map by where tests exist. In Book a class, each step shows which tests check it, what each test checks, and how and when the tests run; Detailed adds the test's name, file and the command that runs it. The step that refunds the card when the booking cannot be saved has no test. The owner leaves a Must do To Do: add one. The inspection report includes testing.

A specialist inspects one scenario

The owner wants the payments consultant, who works with the payment service every day, to look at Book a class before launch. The consultant is not on the team, has no access to the code and has never used the project's repositories. The owner selects the scenario and chooses Send to a Specialist. BigBrain asks whether to send the comments and To Do's with it or just the scenario, and saves one file: the scenario and the part of the map it walks through, with no source code in it. The owner emails it.

The consultant opens the file in BigBrain and chooses Inspect It. The scenario plays for them as it does for the owner, step by step and read aloud, and they can go inside the parts it passes through. They read the owner's comment on the step that saves the booking, add their own on how the payment service can send the same payment event twice, leave a To Do, and in the agent pane write "what if the save fails and the refund fails too?" They have no agent of the owner's to ask, so the question is saved in the file for the owner instead. Their notes are saved into the same file as they go, and they send it back.

The owner opens the returned file. Nothing goes into the map until they say so: they accept the consultant's To Do and comment, and click Ask the Agent on the question, which the agent answers with the step the consultant was looking at as context. A specialist from outside the team has inspected part of the system, and their report is now part of the map. For people who only need to watch, Record as a Movie plays the scenario with the voice on and saves a movie of the map and the step panel that plays on Mac and Windows.

Understanding a change

A fix for the double charge has been committed. The sidebar says the code has moved on; the owner clicks Bring the Map Up to Date. The agent reads only what changed, and the map shows the difference: green for added, red for removed, amber for changed. Explain a change says in plain words what changed, what is affected, and what to test again. The owner knows what to retest without reading the diff.

Onboarding a developer

The developer is new to the project. Instead of a tour from someone busy, they open the map in Detailed mode, play Cancel a booking to see when a refund is made, and go inside the booking part to see its files and functions. The comments other people left are there, with their names. When something is unclear, they ask the agent, and the answer points to the exact code. Snapshots let them compare the map with how it looked at the last release.

Finding a risk and deciding on it

The owner asks "can anyone send emails in the studio's name?" The answer includes a finding: a problem with a severity, the attack that would exploit it (the function that sends emails can be called by anyone who knows its address), the fix in plain words, and how to prove the fix worked. A beacon marks the parts it touches. The owner can approve the fix, defer it, or accept the risk, and the decision is recorded. When the fix lands in the code, the finding's status follows it, and a resolved finding leaves the map but stays in the file.

Closing the loop

After the inspection, the owner opens Review To Do's, ticks the ones to do now and clicks Fix N Marked. BigBrain prepares one prompt, most pressing first, and opens it in the coding agent, Claude Code or GitHub Copilot, in the project. The owner approves each change there and commits. Back in BigBrain, Bring the Map Up to Date reads the new code and marks the fixed To Do's done. The inspection's To Do's went from a note someone left to committed code without anybody copying anything by hand.

What makes it different

The code is still there when you want it. It is the last step, not the first.

  • Compared with diff-based code review. A diff shows lines. BigBrain shows the system, the scenarios the change touches, what else is affected and what to retest. The code is still there when you want it, but it is the last step, not the first.
  • Compared with an architecture diagram. A diagram is drawn once and goes stale. BigBrain's map is built from the code, updated from the commits, and every part cites the files it stands for. It can be walked, questioned and annotated, and it remembers what it has been asked.
  • Compared with chatting with an AI about code. A chat has no shared picture: each question starts from nothing, and the answer lives in a scrolling window. In BigBrain the question carries what you are looking at, the answer is kept on the part it is about, with its citations, and the next question starts from what is known. Three people in an inspection see the same map and each other's notes.

In each case the human stays in charge of the design. The agent explains and proposes; people decide what is good, what must change and how urgently, and they approve every fix in their own tools.

In short

AI can write more code than people can read. BigBrain does not ask people to read it.

It gives them a view of the whole system: a map to walk, scenarios to follow, tests to check, an expert to ask, and a place to say what is good and what needs to change. Two things come of that. The owner can say the system does what they asked for and nothing else, with the promises it must keep checked against the code. And a person who has never written code can understand the system they own, while the developer and the specialist walk the same map at the depth their work needs. That is what a review was always for.

To try it, open the app: the start window offers three demos of the studio, in the order they happen, each with a narrated tour: setting up a new system, inspecting a system, and inspecting a new release. Nothing you do in a demo is kept, and none needs an AI agent. When you want to see your own system, install Claude Code or GitHub Copilot, choose it in Settings, and click New System.
